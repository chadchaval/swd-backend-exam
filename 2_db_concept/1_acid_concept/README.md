## Response Section

อธิบายความหมายของ ACID ทีละตัว

### Atomicity (ความเป็นหน่วยเดียว)

- **ความหมาย:** การทำงานทุกๆ step ในหนึ่ง transaction ต้อง "สำเร็จหมด หรือไม่ก็ไม่เกิดอะไรเลย"
- **ตัวอย่าง:** หักเงิน A แล้วระบบล่มก่อนเพิ่มเงินให้ B จะต้อง rollback ทั้งคู่ ไม่ควรให้เงินหายกลางทาง
- **ฝั่ง DB:** ใช้ commit / rollback ถ้า transaction ล้มกลางทาง DB จะย้อนทุก step ที่ทำไปแล้วกลับให้เอง
- **ฝั่ง App:** เป็นคนกำหนดขอบเขตว่า step ไหนบ้างต้องอยู่ใน transaction เดียวกัน เพราะ DB ไม่รู้เองว่าคำสั่ง 2 อันนี้เกี่ยวข้องกัน

### Consistency (ความสอดคล้อง)

- **ความหมาย:** ก่อนและหลังการทำ transaction ข้อมูลต้องอยู่ในสถานะที่ถูกกติกาทั้งหมด เช่น business rule หรือ ข้อจำกัดในฐานข้อมูลต่างๆ (PK, FK, unique, not null)
- **ตัวอย่าง:** ยอดคงเหลือห้ามติดลบ ถ้าหักเงินจากนาย A ไป B แล้วติดลบ จะต้อง rollback
- **ฝั่ง DB:** บังคับ constraint ที่ประกาศไว้ (PK, FK, unique, not null, check) และปฏิเสธ transaction ที่ทำให้ข้อมูลผิดกติกา
- **ฝั่ง App:** เป็นคนนิยาม business rule เช่น "ยอดคงเหลือห้ามติดลบ" แล้วแปลงเป็น constraint หรือ validation ให้ครบ

### Isolation (ความเป็นอิสระ)

- **ความหมาย:** transaction หลายตัวที่ทำงานพร้อมกัน ต้องไม่รบกวนกันจนข้อมูลเพี้ยน ผลลัพธ์ที่ได้ควรเหมือนกับตอนรันทีละ transaction เรียงกัน
- **ตัวอย่าง:** ป้องกันปัญหาอย่าง อ่านข้อมูลที่อีก transaction ยังไม่ commit, อ่านแถวเดิมซ้ำแล้วได้ค่าไม่เท่าเดิม
- **ฝั่ง DB:** เป็นคนคุมคิวให้เอง เวลามีหลายงานแย่งกันแก้ข้อมูลแถวเดียวกัน
- **ฝั่ง App:** เลือกระดับความเข้มงวดให้เหมาะกับงาน งานที่ห้ามพลาดอย่างตัดเงินหรือตัดสต็อก ต้องสั่งจองแถวนั้นไว้ก่อนไม่ให้คนอื่นแทรกระหว่างทาง

### Durability (ความคงทน)

- **ความหมาย:** เมื่อระบบบอกว่า "สำเร็จ" ข้อมูลนั้นต้องอยู่ตลอดไป แม้ระบบจะพังหลังจากนั้นทันที
- **ตัวอย่าง:** พอ commit แล้ว ข้อมูลต้องไม่หาย แม้ไฟดับ/เครื่องล่มทันที
- **ฝั่ง DB:** เขียนลงบน disk ก่อนตอบกลับว่า commit สำเร็จ และใช้ log นั้นกู้ข้อมูลคืน
- **ฝั่ง App:** ต้องรอผล commit จริงก่อนแจ้งผู้ใช้หรือส่งงานต่อ ไม่ถือว่าสำเร็จตั้งแต่ยังไม่ commit และต้องวางแผน backup
